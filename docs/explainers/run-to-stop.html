Las reglas que lo sostienen

    

      
Docker, siempre fuera de una transacción
El bucle guarda la nueva fase en una transacción corta, la confirma y solo después lanza docker compose. Un arranque de un minuto nunca deja la base de datos bloqueada.

      
Stop solo apunta la causa
POST …/stop escribe STOP_REQUESTED y responde 202 al momento. Quien para y limpia es el bucle, en su siguiente vuelta. Pulsarlo dos veces no cambia nada.

      
Fila bloqueada al cambiarla
Stop y el bucle pueden tocar la misma ejecución a la vez. Los dos la leen con SELECT … FOR UPDATE (findForUpdate…), así que uno espera al otro y nadie borra lo que el otro acaba de escribir.

      
Un solo hilo
Spring ejecuta los métodos @Scheduled en un único hilo. Dos vueltas del bucle nunca se solapan, así que nunca hay dos up o dos down a la vez.

      
Arrancar no es funcionar
Mientras corre, cada vuelta lee el estado de cada nodo con docker compose ps. Si uno se pone unhealthy o desaparece, la ejecución falla con su nombre y se limpia. A los 30 minutos se para sola.

      
Limpiar es comprobar que no queda nada
Tras down -v, el motor busca contenedores, redes y volúmenes con las dos etiquetas, instance y execution, los borra y vuelve a mirar. Si algo queda, la reserva no se libera y lo reintenta.

Las piezas del paso 6b

    
Cuatro clases nuevas y unos pocos cambios en las que ya había. Juntas hacen que el backend sepa qué pasa dentro del experimento mientras corre.

    

      
ComponentStatus
Los cuatro estados de un nodo: STARTING, HEALTHY, UNHEALTHY y EXITED. Su método of(state, health) traduce lo que dice docker compose ps.

      
ExecutionObservations
Lo último que vio el bucle de cada nodo: estado y respuesta. Vive en memoria, por ejecución y por nodo. Escribe solo el bucle, desde su único hilo; lee la API. Se olvida al liberar.

      
ServiceProbe
Hace una sola petición GET / al servicio cuando llega a RUNNING, como evidencia de que responde con tu configuración. Tiempos cortos (2 s y 5 s) y null si no contesta: nunca hace fallar el experimento.

      
ExecutedComponentDTO
Cada nodo en la API, dentro de components[]: clave, nombre, tipo, estado y respuesta. Estado y respuesta valen null hasta que el bucle los ha visto.

Atajos que se sustituirán

    
Están marcados en el código con // shortcut:. Cada uno tiene ya su sitio previsto; el resto del código se queda.

Solo HTTP Service STATELESSExecutionServiceP07. Con los drivers de Redis, PostgreSQL, Worker…, el bucle que rechaza otros tipos desaparece y la comprobación pasa al PlanCompiler.

          
Estado y respuesta en memoriaExecutionObservationsP08. Se guardan como eventos y muestras en la base de datos y llegan al navegador por SSE. La clase se borra.

Infracture en un contenedor (paso 7)

    
En la versión final todo corre en Docker. El backend es un contenedor más: habla con Docker solo a través del proxy y se une a la red de cada experimento para pedirle su respuesta. Por eso la respuesta real solo aparece con el backend en contenedor; con ./mvnw spring-boot:run los experimentos arrancan y paran, pero la respuesta queda vacía.

    

      
docker/Dockerfile
Dos etapas: compila el jar con ./mvnw package y deja una imagen con el JRE, el jar y el CLI de Docker con Compose, que usa el motor. Corre como el usuario infracture, nunca root. Va en docker/, como pide la guía de la Fase 3; en P10 añadirá React y HTTPS.

      
Servicio backend
Perfil app de compose.yaml. Espera a Postgres y al proxy, recibe DOCKER_HOST=tcp://docker-proxy:2375, se llama infracture-backend para que el motor lo una a cada red, publica 127.0.0.1:8080 y corre en solo lectura y sin capacidades.

      
Cómo se arranca
docker build -t infracture/demo-app:0.1.0 demo-app una vez, y después docker compose --profile app up -d --wait --build. Se para con docker compose --profile app down. Los pasos están en la guía de desarrollo.
